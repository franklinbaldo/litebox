# Android userspace M3 — APK headless smoke

Parent: #25. Stacked on M2.

M3 is the first milestone that accepts a real `.apk` file as input.

It deliberately does **not** claim Android application lifecycle compatibility. The APK is treated as the standard Android ZIP container containing `AndroidManifest.xml` and one or more `classes*.dex` files. The whole APK is placed on ART's class path and an explicitly named Java `main()` class is invoked headlessly.

That distinction matters: a green M3 proves that LiteBox can carry Android bytecode packaged as an APK through bionic + ART on Windows userland. It does not yet prove `Activity`, package manager, Binder services, zygote, `system_server`, graphics, Play Services, or device certification.

## Prepare

Use a deliberately simple x86_64-compatible APK that contains a class with:

```java
public static void main(String[] args)
```

Then:

```powershell
python scripts/android/prepare_apk_probe.py `
  --runtime-tar .\android-art-runtime.tar `
  --apk .\smoke.apk `
  --output .\android-apk-smoke.tar
```

The preparation step fails unless the input is a ZIP container containing both `AndroidManifest.xml` and at least one `classes*.dex` entry.

## Run

```powershell
powershell -File scripts/android/run_apk_probe.ps1 `
  -Tar .\android-apk-smoke.tar `
  -MainClass dev.litebox.ApkSmoke
```

## Acceptance

- [ ] the input is an actual `.apk` container with Android manifest and DEX payload
- [ ] the entire APK, not an extracted replacement JAR, is placed on ART's class path
- [ ] ART loads the named class from the APK and invokes `main()`
- [ ] stdout and exit status are deterministic
- [ ] execution remains ordinary Windows x86_64 userland with no elevation, WSL, hypervisor, QEMU, or Android kernel driver
- [ ] a malformed APK, APK without DEX, missing class, or ART failure produces a distinct failure rather than a false green

## What comes next if M3 is green

Only after this milestone is demonstrated should #25 advance toward the Android framework boundary: Binder device/ioctl semantics, service manager, zygote, package manager and eventually a real app lifecycle (`Activity`/service). Those should be separate PRs because they introduce qualitatively different compatibility requirements.

M3 is therefore the requested **"ready to test with an APK"** gate, not the claim that arbitrary Android apps already run.
