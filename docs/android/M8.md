# M8 — Software-rendered Android display on Windows

Parent RFC: #25. Stacked on M7 / PR #34.

## Goal

Turn the headless Activity boundary into visible pixels without requiring GPU passthrough, a VM, a Windows kernel driver or administrator privileges.

## Guest graphics path

Keep Android surface/buffer ownership on the guest side and surface only the composed result to LiteBox:

```text
Activity / View hierarchy
  -> Surface / BufferQueue
  -> Android composition path
  -> software / virtual display target
  -> bounded RGBA framebuffer
  -> LiteBox android-display capability
  -> Win32 HWND
```

Use real Android graphics components where feasible. Where hardware would normally exist, provide the smallest narrow virtual/HAL backend needed to expose a software target.

## First display contract

Start with one fixed virtual display, initially 480x800, one pixel format, bounded buffers and explicit frame ownership. No resize, rotation, multiple displays, GPU acceleration or arbitrary host handle exposure is required.

The Windows backend presents pixels in a normal user-mode window. The guest never receives an HWND or unrestricted host graphics object.

## Diagnostics

Every frame boundary should be observable with:

- dimensions and stride;
- pixel format;
- frame sequence number;
- buffer lifetime/state;
- dropped/late frame counters;
- optional deterministic frame hash for CI/offscreen verification.

## Acceptance

- [ ] Activity from M7 obtains a valid rendering target
- [ ] Android produces a complete software-rendered frame
- [ ] LiteBox receives the frame through a typed `android-display` boundary
- [ ] a normal non-admin Win32 window displays the Activity
- [ ] offscreen CI can verify a deterministic frame hash without a desktop session
- [ ] no GPU acceleration is required
- [ ] no mouse/keyboard input implementation is required to pass M8
