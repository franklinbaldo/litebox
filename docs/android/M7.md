# M7 — Headless framework and Activity lifecycle

Parent RFC: #25. Stacked on M6 / PR #33.

## Goal

Cross the boundary from “Android runtime + Binder works” to “an ordinary APK can be launched through real Android framework contracts”, while still keeping graphics out of scope.

## Service graph

Run real pinned AOSP components wherever practical. Bring them up incrementally rather than trying to satisfy every daemon from `init.rc`:

1. `servicemanager` (already proven by M6);
2. property/logging/shared-memory prerequisites;
3. zygote;
4. only the `system_server` services required for package lookup, process launch, resources and Activity lifecycle.

Do not replace ActivityManager, PackageManager or zygote with bespoke LiteBox mocks merely to make the smoke pass if the real component can run on the substrate.

## APK boundary

The fixture APK must exercise the ordinary app-facing path:

- deterministic install/mount or package registration;
- package identity and resource setup;
- classloader/application process setup;
- spawn through the zygote path;
- `Application` lifecycle;
- `Activity` create/start/resume;
- Binder calls to the required framework services.

No display backend is required yet.

## Headless rendering contract

The test Activity may create a View hierarchy and request a rendering target, but M7 succeeds before host pixels exist. The expected terminal state is an explicit headless/display-unavailable boundary, not a crash caused by missing framework infrastructure.

## Acceptance

- [ ] real zygote starts on LiteBox
- [ ] minimal required system service graph becomes stable
- [ ] fixture APK is resolved through package/framework contracts
- [ ] app process is spawned through zygote
- [ ] `Application` starts
- [ ] one Activity reaches resumed state
- [ ] Activity can create its UI tree without a host display backend
- [ ] missing display is reported as the next explicit capability boundary
- [ ] no Win32/window/input implementation is required to pass M7
